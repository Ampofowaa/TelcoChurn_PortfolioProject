# Data Handling and DVC Pipeline Conventions

Moved verbatim from CLAUDE.md, which keeps a one-line summary of each rule and links here. These rules are binding: read this file before changing the code it covers.

## Data Handling

- **`datasets/raw/` is read-only.** Never modify, overwrite, or delete any file there.
- **The raw CSV is committed to Git; DVC owns only derived artifacts.** DVC lists `datasets/raw/*.csv` as a stage **`dep`** (hashed into `dvc.lock`, re-runs the DAG on change), not an **`out`** (cached, gitignored, remote-backed). A dep may be any path in the repo. The file is 977 KB, static, and read-only — none of DVC's reasons to own raw data apply, and gitignoring it would break fresh-clone reproducibility and Phase 11's CI. `datasets/processed/` is gitignored; DVC owns it as stage output.
- **No DVC remote is required before Phase 12.** A local cache is the full configuration. Phase 12 *adds* an S3 remote for shared caching; it is not a migration, and nothing depends on it.
- **Postgres is a materialised cache of the CSV, never a source of truth.** Its contents are fully determined by the raw CSV + `sql/schema/` + `data/ingest.py`. It cannot be a DVC `out` (outs are files); the `ingest` stage emits `reports/ingest_receipt.json` instead. A hand-edited `customers_raw` is invisible to `dvc repro` — rebuild with `dvc repro --force`.
  - **The same blind spot applied to a genuinely fresh Postgres/MLflow pair, not only a hand edit — caught during Phase 8's fresh-clone check and fixed by gitignoring the six per-cycle receipts, rather than deferring it to Phase 10.** `reports/ingest_receipt.json`/`validation_receipt.json`/`train_receipt.json`/`calibrate_receipt.json`/`eval_receipt.json`/`error_analysis_receipt.json` stay `cache: false` (still small, deterministic, written to `reports/` on every run) but are no longer git-committed. Committed, they used to arrive on a brand-new clone pre-populated and hash-matching — `dvc repro` saw "nothing changed" and skipped `ingest`/`train`/`calibrate` even though the fresh Postgres had no `customers_raw` rows and the fresh MLflow had no matching run; the failure surfaced two stages downstream and looked unrelated (`split` failing with *"requires at least 2 classes to stratify; got 0"*), because DVC's staleness check had no way to verify the external system a `cache: false` receipt describes is the same one it was written against. Gitignored, a fresh clone has no receipt on disk at all — DVC's own missing-output check sees the `out` absent and reruns `ingest`/`train`/`calibrate`/`evaluate`/`error_analysis` for real on the very first `dvc repro`, the same way it already does for `split`/`features`'s cached, gitignored outs. No manual `--force` workaround is needed for this case anymore; **the hand-edited-`customers_raw` case above still is** — the receipt file itself is untouched by a direct DB edit, so it still exists on disk at its recorded hash regardless of git status, and DVC still has no way to see the mismatch. The traded-away benefit: a past cycle's `run_id`/`model_version` is no longer inspectable straight from git history — acceptable, since MLflow is already this project's system of record for run identifiers, and a receipt was only ever meant as a same-cycle bootstrap pointer (see the MLflow Model Registry section above), not an archival record.
- **`customers_crm` is a derived, serving-time-only table — never a second source of truth, and never read by anything in the training pipeline.** Populated by `serving/crm_data.py::generate_crm_rows` (seeded `random_state: 42` from `configs/serving/api.yaml`'s `crm:` block), it applies light, deterministic nudges to a copy of `customers_raw` — tenure advances +1–6 months, contract term occasionally upgrades (never downgrades), `totalcharges` accrues accordingly, everything else held fixed — simulating a customer's account having moved forward since the frozen training snapshot was taken. It exists because a live customer-lookup endpoint must not silently reuse the training table as if it were current: `serving/customer_lookup.py::lookup_customers` reads `customers_crm` exclusively, backing both `GET /customer/{id}` and `/predict/batch`'s ID-resolution path — never `customers_raw`. Regenerate with `make crm-data` (after `db-up` + ingest) — safe to re-run, since the fixed seed makes every regeneration produce the same nudges; only `crm_snapshot_at` (stamped fresh each run) genuinely changes. A durable, joinable record tying a specific request to the `customers_crm` row it scored is `serving/prediction_log.py`'s `prediction_log` table (Phase 10a-i): every `/predict`/`/predict/batch` call is captured, including the exact `feature_snapshot` scored, via a `BackgroundTasks` write that fires after the response is sent.
- **`datasets/processed/telco_churn_features.parquet`** is the processed-features artifact, written by `features/build.py`'s `__main__` (`dvc repro features`) — the DVC `features` stage's declared, cached output. Read it through `features/accessor.py::load_features()`, never by constructing the path inline. `cfg.paths.processed_data` itself is readable only by `features/accessor.py` and `data/split.py` — enforced by `tests/unit/test_architecture.py::test_processed_data_path_is_read_only_by_its_canonical_resolvers`.
- **TotalCharges gotcha:** the raw CSV has `TotalCharges` as a string with whitespace for 11 zero-tenure customers. Coerce to numeric first, then impute with median — never drop.
- **Target column** is always named `churn` (binary: 0/1).
- **Class imbalance handling is required** — never train a model without it.
- **Random state is always 42** for reproducibility across all splits, samplers, and models. No `src/` call site hardcodes the literal — each stage reads its own `random_state`/`random_seed` key from its own config file (`configs/config.yaml`'s top-level `random_seed` for the dev/test split and CV folds; each of `configs/{calibration,threshold,evaluate,training/feature_selection}/default.yaml`'s own `random_state` for its stage), deliberately kept as separate keys rather than one shared or interpolated value — DVC hashes each stage's `params:` independently, so unifying them would either rerun the whole DAG on any single-stage seed edit or make the dev/test split reachable from what should be an isolated per-stage change. A hardcoded literal other than `42` is still rejected — enforced by `tests/unit/test_architecture.py::test_random_state_literals_are_always_42`.

## DVC Pipeline

`dvc.yaml` wraps the straight-line, file-producing half of the modelling lifecycle — `ingest → validate → split → features → train → calibrate → threshold → evaluate → error_analysis`, nine stages — as a content-hashed DAG. **DVC tracks what the DAG consumes; MLflow owns terminal artifacts; figures are never DVC outs.** Concretely:

- **A stage's `outs:`/`metrics:`/`plots:` are small, deterministic, local-inspection artifacts** — receipts (`reports/*_receipt.json`, `cache: false`), the two cached per-row parquets (`split_manifest.parquet`, `telco_churn_features.parquet`), `reports/metrics_summary.json`, `reports/plots/decile_lift.csv`, `reports/policy/threshold.yaml`, `reports/dev_oof_diagnostics.json`. Everything with real evidentiary weight — the model itself, `training_manifest.json`, `calibration_summary.json`, SHAP values, sealed-test `metrics.json`/`economics.json`, `drift_reference.json`, `model_card.json` — is an MLflow run/`LoggedModel` artifact, resolved by `run_id`/`logged_model_id`, never by a fixed `reports/` path (see MLflow Model Registry above).
- **Figures are excluded from DVC entirely** — reliability diagrams, SHAP plots, and every other rendered chart are untracked MLflow artifacts under a run's `figures/` path, re-rendered fresh on the next genuine cycle. They carry no data DVC needs to cache or hash: nothing downstream reads a figure back in, and CLAUDE.md's "persist the evidence, not just the conclusion" rule already requires the underlying array (`dev_oof_predictions.parquet`, `shap_values.parquet`, ...) to be logged separately for exactly this reason.
- **Registration (`register.py`'s mint/tag/flip) stays outside the DAG** — a registry alias is not a file, so it cannot be expressed as a DVC stage. A full manual cycle is five steps, not one `dvc repro`: **(1)** `dvc repro calibrate` — naming `calibrate` as the target (not a bare `dvc repro`) reproduces exactly its upstream chain, `ingest → validate → split → features → train → calibrate`, and exits 0; it never attempts `threshold.py`/`evaluate.py`, which resolve their model via a *registered version* that nothing has minted yet, so there is no error to see on a normal first run — a bare `dvc repro` would instead attempt the whole graph in one call and genuinely fail there; **(2)** `register.py` (`make register-challenger`) — mints that version, tags it `pending`, points `challenger` at it; needs no explicit `register.run_id` for this default path either, since it resolves from `calibrate.py`'s own receipt the same way `dvc repro`'s stages do (an explicit `register.run_id=<id>` only matters for targeting a different historical calibration run); **(3)** `dvc repro error_analysis` — naming `error_analysis` as the target reproduces its upstream chain in turn; `calibrate` and everything before it are already cached, so what actually executes is `threshold → evaluate → error_analysis`, each resolving the version step 2 minted; **(4)** `models.review` (`make review VERDICT=... APPROVER=... NOTES=...`) — the human verdict, stamped on top of the automated gate verdict `evaluate` already computed in step 3; **(5)** `register.py register.model_version=<version>` (`make register MODEL_VERSION=<version>`) — reads the gate verdict + human review, flips `champion` or tags rejected. Steps 4-5 read as generically "review then register," but review is not spliced *between* calibrate and threshold — it runs after step 3, once `evaluate`'s verdict exists to review.
- **`params:` exemptions — four categories, none of them declared, by design:**
  1. **Env-resolved keys** (`mlflow.tracking_uri`, `database.url`) — both are `${oc.env:...}` interpolations; DVC parses `params:` files with its own YAML reader, not Hydra's, so a declared env-resolved key would hash the literal `${oc.env:...}` string forever rather than the value it actually resolves to — silently un-tracking the param while looking handled.
  2. **Identity tokens** (`run_id`, `model_version`, `logged_model_id`, `eval_run_id`, `error_analysis_run_id`, ...) — these name *which artifact from a prior cycle* a stage reads, not a modelling decision. Declaring one would make every stage rerun the instant any upstream stage produces a new run, which is what the receipt-based `deps:` edges (`reports/train_receipt.json`, `reports/calibrate_receipt.json`, ...) already express correctly.
  3. **`paths.*` — the whole prefix**, unconditionally. These keys restate `outs:`/`deps:` locations already declared by path elsewhere in the same stage, and several are `${...}`-interpolated (`${paths.reports}/figures`), which DVC cannot hash meaningfully. A repointed `paths.*` key is a correspondence question (does `dvc.yaml`'s own literal path still agree with it?), not a params-invalidation one — that is `test_paths_config_matches_dvc_yaml_literals`'s job, not `params:`'s.
  4. **`mlflow.experiment_name`** — cosmetic/organisational; renaming it changes nothing about what any stage computes.

  This is enforced structurally, not by convention — `tests/unit/test_architecture.py::test_params_match_reads` asserts every resolvable `cfg.<key>` read in a stage's real import closure is declared (`read ⊆ declared`, hard-fail from day one; the reverse direction, phantom-param detection, is advisory/future work — a clean result there is not proof nothing is over-declared). `test_loaded_configs_are_declared` covers the file-granular case for `configs/costs.yaml`/`configs/model_promotion.yaml`, which are read via explicit `OmegaConf.load(<path>)` and never enter the composed `cfg` tree the key-granular guard scans. `test_stage_deps_cover_the_real_import_closure` is the same idea applied to `deps:` — every `telco_churn.*` module a stage's entry point transitively imports must be declared or named in a standing exemption.
