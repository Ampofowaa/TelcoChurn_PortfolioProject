# Modelling Invariants and Serving Policy

Moved verbatim from CLAUDE.md, which keeps a one-line summary of each rule and links here. These rules are binding: read this file before changing the code it covers.

## Modelling Invariants

These are written policy — not notebook conventions — and must be preserved in all `src/` code:

- **Test set touched once.** Only `models/evaluate.py` may bind the test half of `data/split.py::partition()`'s `(dev_df, test_df)` return, or call `test_ids()` — enforced by `tests/unit/test_architecture.py::test_only_evaluate_binds_the_test_partition` and `::test_test_ids_is_never_called_outside_evaluate`. Downstream modules may still carry local variables literally named `y_test`/`X_test` (`error_analysis.py` does) — those are sourced from `evaluate.py`'s already-stamped `test_predictions.parquet`, a naming choice on scored output, not a second import of the sealed split. Under continuous retraining (Phase 10), a **routine** `performance_check.py`-gated cycle never uses the sealed test set as its promotion-comparison surface — the binding challenger-vs-champion comparison runs on the fresh `reserve` cohort, this project's bounded stand-in for the industry-standard rolling/walk-forward holdout (test slice always current, never reused across cycles), which the static, timestamp-less dataset cannot support directly (full treatment: `ANALYSIS.md` §9 #13). `performance_check.py` still *scores* the sealed set each routine cycle, but only for cross-cycle diagnostic metrics (logged under `dataset="sealed_test"`, demoted to a `sealed_test_diagnostic` block in `metrics.json`/`economics.json`); nothing in the promotion decision reads those numbers, so this does not consume the seal as evidence. A **rare** `evaluate.py`-gated cycle (manual trigger or `COMMITTED_FEATURES` mismatch) still reuses the original sealed set as its comparison surface every time it fires — a documented, unenforced erosion risk (`ANALYSIS.md` §9 #13), mitigated only by "rare" being infrequent by convention.
- **`evaluate.py` resolves its model by explicit `run_id` or version number, never by alias.** An alias is a moving pointer — under Phase 10's monthly retrain, `challenger` moves to a new candidate every cycle, so resolving "whatever `challenger` currently points at" can silently evaluate a different model than the one a caller intended. Log the resolved version into `reports/metrics.json` so metrics are attributable to a specific artifact. A refactor to `models:/telco-churn-pipeline@challenger` is a correctness regression, not a simplification — enforced by `tests/unit/test_architecture.py::test_evaluate_never_resolves_a_model_by_alias`.
- **One metric drives selection.** PR-AUC (average precision) is the sole criterion for model selection, Optuna tuning, and champion promotion. If two metrics point in different directions, PR-AUC wins — mixing selection signals introduces cherry-picking risk.
  - **Guardrails may veto; they may never promote.** Three metrics — recall at the shipped threshold `t*`, Brier, and the **calibration slope** — can *reject* a model that PR-AUC admitted, on the grounds that it is not a valid artifact (it misses too many churners at the operating point, it is probabilistically unskilled, or its posteriors are not honest). None can ever move the decision in the admitting direction: no model is promoted *because* its Brier improved. A veto-only guardrail cannot cherry-pick — it can only cost a promotion, never buy one — which is why this does not breach the invariant above. All remaining metrics (precision, F1, ROC-AUC, ECE, lift, expected value) are diagnostics: reported, never binding.
  - **Two calibration guardrails, because Brier alone cannot do the job.** `Brier = reliability − resolution + uncertainty` (Murphy) blends calibration with *ranking*, so a challenger that ranks better and calibrates worse **improves its Brier** and passes a Brier-only check. That failure is not cosmetic here: `t* = c/(r × LTV)` is Bayes-optimal only against honest posteriors, so a silently miscalibrated champion means the shipped threshold has stopped being the right decision rule — and no PR-AUC check would reveal it, because ranking is precisely what still looks fine. The **calibration slope** (regress `y` on `logit(p)`; 1.0 is perfect, < 1 is overconfident) is binning-free, parameter-free, and cannot be bought with better ranking, which is what makes it gate-worthy where **ECE is not** (binning-dependent, improper, biased — reported, never gating).
  - **The gate is specified in one place: `ANALYSIS.md` §0.** Its bars, its two regimes (cold start with no incumbent champion vs. comparative against a serving one), and the rationale for each live there. `models/gate.py` implements it as a pure function (`decide_promotion`), `models/evaluate.py` calls it once the sealed-test metrics exist, and `models/register.py` **reads** the persisted verdict rather than recomputing it; `PROJECT_PLAN.md` says where in the lifecycle each runs. None restates the rule — if a bar needs changing, change §0 and let the others follow.

## Serving

Written policy for `serving/predict.py`/`serving/app.py` (Phase 9+), same standing as Modelling Invariants above — these govern how a promoted model actually gets scored against traffic, not just how it gets promoted. Full mechanism diagrams and a real evidence log live in `docs/architecture.md`'s Shadow/Canary Serving section; this section is the policy summary, not a duplicate of it.

- **`resolve_champion_model`/`resolve_challenger_model` are the single indirection point.** No call site anywhere resolves `models:/telco-churn-pipeline@champion` or `@challenger` directly — every read of "which version is currently serving" goes through one of these two functions, so there is exactly one place that can ever disagree with the registry. Both poll on a TTL and diff the target version's MLflow-logged dependencies against what's actually installed (`models/environment_parity.py::diff_environment`) before hot-reloading in place — a promotion is just an alias flip, and nothing about it requires restarting the process. **Fail-open on a refresh problem, fail-closed on the initial load**: a later poll failure keeps serving the last-known-good bundle and logs a warning, never flips an already-healthy process to `503`; the very first load has no last-known-good to fall back to, so it raises and retries with backoff instead. A challenger-side problem is never a reason to disrupt champion traffic either way.
- **The SHAP explainer and the threshold policy travel inside the same `ModelBundle` a reload swaps in one piece — never cached independently of the model.** A `TreeExplainer` cached for the process's *lifetime* rather than its *currently-loaded model* would keep explaining the old booster after the probability next to it already reflects a new one; a threshold cached across a promotion would judge a new model's score against a `t*` derived for a different version. Both are resolved from the champion's own MLflow run in the same pass that resolves the model, never from a fixed local path — `policy_config.py::load_threshold_payload(run_id, cfg)` reads `runs:/{run_id}/threshold/threshold.json`, the same discipline `drift_reference.json`'s champion-alias rule already establishes: a fixed path doesn't roll back with an emergency rollback, a versioned artifact does.
- **Shadow and canary are two independent, config-gated toggles (`configs/serving/api.yaml`), not one flag with two readings.** Shadow scores every request against the challenger for comparison but never serves its opinion — zero routing risk, pure observability. Canary actually routes a consistent-hash slice of traffic to the challenger — bounded routing risk, needed because some failure modes only surface once a model's output has real consequences. Both default off. Canary bucketing is `sha256(f"{customerid}:{challenger_version}") % 10_000 < fraction * 10_000` — salted with the **challenger's own `model_version`**, never a bare customerid hash, so the canary population reshuffles the next time `challenger` moves to a different version instead of being the same customer subset on every canary this project ever runs. A request with no `customerid` is never canary-routed — no targeting key means the default variant (champion), the same rule feature-flag platforms (LaunchDarkly, OpenFeature) use.
- **`customerid` is a pass-through identifier, never a model feature — same separation `features/schema.py::CustomerFeaturesSchema` enforces at training time.** It rides alongside the request/response without being fed into `predict_proba`, and it is what canary bucketing hashes on — precisely the stability a feature must never have.
- **`decision` and `contact` are two separate output fields, never one flag reinterpreted per branch.** `decision = proba >= t*` is computed once and is never touched by capacity. `contact` ranks the `decision`-true set by expected value and cuts at `min(contact_capacity, floor(campaign_budget / cost))` — a row can carry `decision: true, contact: false` (the model flagged them, capacity didn't reach them this cycle), and that state must stay visible on the wire, never silently collapsed into "no action needed." Both are `bool` on the wire, never a string standing in for one.
- **The three data routes (`/predict`, `/predict/batch`, `/customer/{id}`) may require an API key; the three probe routes (`/health`, `/ready`, `/metrics`) never do.** An infra probe that needs a credential to answer "is this alive" turns a control-plane outage into an availability one. `auth.enabled` defaults off (`configs/serving/api.yaml`) for local `docker compose up` and the public Docker Hub pull-and-run use case — flip it on, with a real key, before exposing the API anywhere actually reachable.
- **Routes are unversioned through Phase 9 on purpose (`/predict`, not `/predict/v1`) — adopt `/v1` no later than Phase 11.** There is no external consumer yet; that stops being true the moment CI or a deployed caller starts treating this API as a contract, and a breaking schema change after that point has no migration path. Recorded here so it is a scheduled decision, not a "never came up" gap discovered after Phase 12 ships.
- **`docker/api/Dockerfile` builds from the project's own `uv.lock`, never a champion-specific `requirements.txt` resolved at build time.** The champion's MLflow-logged `requirements.txt` is used only as the hot-reload guard's *comparison input* (diff against what's installed), never as the image's build source — treating the image's dependencies as ordinary, CI-tested, project-versioned software is what lets the hot-reload design work at all. A container whose libraries were pinned per-model-build would have no stable "installed environment" for the guard to diff a new champion's logged deps against.
