# MLflow Model Registry Conventions

Moved verbatim from CLAUDE.md, which keeps a one-line summary of each rule and links here. These rules are binding: read this file before changing the code it covers.

## MLflow Model Registry

- **Tracking backend:** **Postgres**, via the MLflow server (`docker-compose.yml`: `--backend-store-uri postgresql://…@postgres:5432/mlflow`). `mlruns/` is the **artifact** store only (`--artifacts-destination`), not the backend — do not describe it as the tracking backend. Phase 12 swaps Postgres for RDS and the artifact root for S3: a URI change, not a migration off files.
  - **The fallback must stay a database backend.** `configs/config.yaml` resolves `tracking_uri: ${oc.env:MLFLOW_TRACKING_URI,sqlite:///mlflow.db}`; without `.env` or the infra profile (fresh clone, CI) that SQLite default is what runs. **Never default it back to a bare path like `mlruns`** — that is MLflow's file store, which as of 3.14 is in maintenance mode, **raises on use**, and does not receive new features (including the `LoggedModel` entities the evaluation logging depends on). SQLite is not an alternative to Postgres; it is the zero-infra fallback with the same SQLAlchemy feature surface, so local/CI never diverges from served mode.
- **Registered model name:** `telco-churn-pipeline`
- **Production alias:** `champion` — the FastAPI service loads whichever run carries this alias at startup.
- **Challenger alias:** `challenger` — used during evaluation before promotion.

### Run artifacts vs. registry versions

The **run** is the experiment record; the **registry** is the deployment surface. Everything fitted during a training cycle is logged to the run and is retrievable there via `runs:/<run_id>/model` — nothing needs registering to be loadable. A registered model version answers exactly one question: *could this be serving traffic right now?*

- **Model-version tag `promotion_status: pending | promoted | rejected`, set to `pending` at the moment the version is minted.** A version is a valid rollback target **iff** it carries `promoted`. This is the standard registry approval-state field — SageMaker ships it as `ModelApprovalStatus`, and it is exactly what MLflow's own docs prescribe to replace the deprecated `stages` (aliases for the deployment pointer, tags for the version's state). The registry is *supposed* to hold unapproved candidates: CI needs a stable artifact reference to validate against, the audit trail wants failed candidates recorded rather than vanished, and Phase 10's Prefect flow passes a model URI between steps. **Registering an unvalidated candidate is normal; leaving it unlabelled is the defect.**
  - **`pending` is the mint-time default because the safe state must be the one you get for free.** A `rejected` tag written only on the failure path is a tag that the next abort path will forget to write — and a crash, an OOM, or an unhandled exception writes nothing at all. Defaulting to `pending` makes every one of those failure modes fail safe: you never have to remember to mark something *bad*, only to mark something *good*, and that step is already load-bearing.
  - **The fail-safe default produces residue by design, and that residue has a defined drain: stale `pending` versions are reaped.** The same property that makes `pending` safe — a crash leaves it behind — means every crashed evaluation, OOM, or unhandled exception deposits a version stuck at `pending` forever. `pending` is meant to be *transient*: a version resolves to `promoted` or `rejected` within its own cycle, so **a `pending` version older than one training cycle is definitionally a crash artifact**, carrying no rollback value (not `promoted`) and no audit value (never decided). Those — and only those — may be pruned. This is *retention hygiene, not size management*: `promoted` versions are the rollback surface and are kept unconditionally; `rejected` and `dev`-scope versions are the audit trail and are kept; **the reap touches `pending` orphans exclusively.** The point is rollback *legibility*, not disk: unreaped orphans lengthen and pollute the version list a human scans under pressure, which is the exact hazard the tag-based rollback rule below exists to prevent — so leaving them to accumulate quietly erodes that rule. No automated reaper is required for this project; a manual prune utility (surfaced in the Phase 14 runbook) is the intended scope, and it must filter on *both* `promotion_status == pending` **and** an age threshold, never on version number.
  - **Emergency rollback selects on the tag, never on version arithmetic.** `set_registered_model_alias(name, "champion", version=N-1)` — *"the previous number"* — is the command that goes wrong: a rejected or crashed evaluation cycle leaves a `challenger`-registered version with no `champion` alias and no `promotion_status: promoted` tag, which is **indistinguishable in a version list from a legitimate previous champion** if you go by version number alone — both are just "some earlier integer." The command then succeeds, the service restarts cleanly, and it silently serves a model that failed its gate. Roll back to the highest version tagged `promotion_status: promoted`.
- **Validate, then promote — never promote, then validate.** The alias flip is the moment traffic moves; nothing unverified may sit behind it. Load the candidate by **explicit version URI** and run the full smoke check (schema, output shape/range, golden-prediction parity) *before* `set_registered_model_alias`. Flip only on a pass, then re-assert parity **through the alias** as a thin confirmation the pointer landed — and **roll the alias back if that fails**. Flipping first and checking afterwards is a Kubernetes readiness probe that runs after the pod is already taking traffic; it leaves `champion` pointing at a model that failed its serving check, and Phase 9's FastAPI loads `models:/telco-churn-pipeline@champion` at startup.
- **One registration per training cycle, at the point the artifact becomes serving-shaped.** Calibration is part of the model's inference graph, not a downstream consumer of it — `CalibratedClassifierCV(Pipeline([preprocessor, lgbm]))` is one sklearn estimator with one `predict_proba`, logged with one `log_model` call. The uncalibrated pipeline is a *stage of construction*, not a model that lost a comparison: it is logged to the run for auditability and **never registered**.
- Concretely: **Phase 5 logs, does not register** (no `registered_model_name=`, no alias). **Phase 6 `calibrate.py` fits and logs the calibrated pipeline — a pure, deterministic file transform — and performs no registry write of its own**, ever, from its own process. `register.py` is the single entry point for every registry write in the cycle, run as its own CLI step (`python -m telco_churn.models.register`) *after* `calibrate.py` has already exited, never called from inside it: given `register.run_id` (or defaulting to `calibrate.py`'s own `reports/calibrate_receipt.json` when omitted), `register_challenger` mints the version, tags it `promotion_status: pending` at mint time, and points `challenger` at it; given `register.model_version` instead (an already-registered version — the two are mutually exclusive on the same CLI, dispatched by which one is set), `run_registration_step` runs the promote/reject path described next. **Phase 7 `evaluate.py`/`error_analysis.py` → `register.py`** then closes the cycle — `evaluate.py`/`error_analysis.py` write no model-version tags either (see the tag-ownership rule below); `register.py` reads their `reports/eval_receipt.json`/`reports/error_analysis_receipt.json` bootstrap pointers, tags the model version, checks the human review verdict, and either flips `champion` onto the version it minted, or leaves it rejected. An alias is a unique pointer per model name — re-aliasing does not create a second challenger, it silently orphans the previous version.
- **The gate measures the exact artifact it promotes.** The promotion decision is computed on the registered version's sealed-test metrics, and a pass flips `champion` onto that same version — there is no second fit and no second artifact standing in for the one that was measured.
- **The decision precedes the action, structurally.** The gate lives in `models/gate.py` as a **pure function** (`decide_promotion`), is called by `evaluate.py` at the moment the sealed-test metrics exist, and is logged as `promotion_decision.json` onto `evaluate.py`'s own `evaluation` run — carrying the regime, the per-criterion breakdown, the evaluated model version, and a `metrics_content_hash` stamp. It carries no `review` field: the human verdict is a separate, append-only document, **`promotion_review.json`**, logged onto the same eval run by `models/review.py` — a standalone CLI, independent of Jupyter, and the sole entry point that writes it (notebook 05 displays the diagnostics a reviewer needs but does not itself stamp a verdict) — via `gate.py::record_review` — `{eval_run_id, metrics_content_hash, entries: [{verdict, notes, approver, reviewed_at}, ...]}`. Append-only because `log_dict` to a fixed artifact path overwrites: a `rejected` stamp later overridden by `approved` must not vanish without trace. `register.py` **reads** `promotion_decision.json` and `promotion_review.json["entries"][-1]` rather than recomputing or re-deriving either, aborting if `promotion_decision.json`'s embedded model version does not match the version being registered. A human `rejected` verdict is routed through the same `_tag_rejected` path as a gate failure — left at `pending` it would be indistinguishable from a crash artifact. Two independent evaluations of the same rule are how the rule becomes two rules.
- **`register.py` resolves every cross-cycle artifact by tag, never by a local `reports/` path — and it is the only module that writes a model-version tag.** `eval_run_id`, the four gate criteria, and `error_analysis_run_id` are tagged onto the model version by `register.py` itself (not by `evaluate.py`/`error_analysis.py`, which write no registry tags at all), resolved from the tag if a prior invocation already wrote it, else from `reports/eval_receipt.json`/`reports/error_analysis_receipt.json` — the same first-invocation bootstrap role `reports/calibrate_receipt.json` already plays for `threshold.py`/`evaluate.py`/`error_analysis.py`'s own input resolution — verified against the model version and tagged immediately, so every later read goes through the tag and never the receipt again. This mirrors `calibrate.py`'s `logged_model_id` tag, since `ModelVersion.model_id` doesn't auto-populate in OSS MLflow 3.14 and nothing else creates a version-to-run link. `register.py` reads `promotion_decision.json`/`metrics.json`/`economics.json`/`test_predictions.parquet` via `runs:/<eval_run_id>/...` and `error_analysis.json` via `runs:/<error_analysis_run_id>/...`, cross-checking each against the `model_version` being registered (a `metrics_content_hash` stamp for the former, a `model_version` field for the latter). `reports/` is still written by every step as a human-inspection mirror, but beyond the receipts' one-time bootstrap role `register.py` never reads it back — a fixed local path reflects whichever run last executed `evaluate.py`/`error_analysis.py` on this machine, not necessarily this model_version's own cycle, the same staleness failure mode the `drift_reference.json` rule below exists to prevent. **A refactor back to a local `reports/` read is a correctness regression, not a simplification** — same footing as `drift_reference.json`'s champion-alias rule and `evaluate.py`'s resolve-by-`run_id` rule.

- **Logged artifacts per run (every training cycle, Phase 5+):** model (pyfunc), `feature_space.txt`, `feature_columns.txt`, `preprocessing.pkl`, `training_manifest.json`.
  - `feature_space.txt` — full **feature space**: every column `build_feature_df` produced before selection (the complete output of the Phase 4 feature pipeline).
  - `feature_columns.txt` — **model input space**: the subset that survived `select.py` and entered the `ColumnTransformer`. The diff between `feature_space.txt` and `feature_columns.txt` is what selection dropped for that run — a per-run audit trail that requires no git lookup.
  - `preprocessing.pkl` — fitted `ColumnTransformer`; encodes the exact transformations applied to the model input space at training time.
  - `training_manifest.json` — **engineering audit trail**: git SHA, `data_content_hash` (sha256 of the processed features parquet, via `features/accessor.py::features_sha256()` — independent of DVC, since pipeline-stage outputs are tracked in `dvc.lock`, not a per-file `.dvc` sidecar, so no such sidecar for this file will ever exist to hash), model family, full hyperparameters, `feature_space`/`feature_columns`, CV PR-AUC, a `model_family_committed` section (`model_family`, `decision_reference: "ANALYSIS.md §4a"`, `decision_run_id` — the frozen model-family decision referenced via `models/train/common.py::COMMITTED_MODEL_FAMILY`/`COMMITTED_MODEL_FAMILY_DECISION_RUN_ID`, never recomputed live — `candidates.py`/`comparison.py` run only from `notebooks/03a-model-selection.ipynb`'s on-demand review, not the automated pipeline), `logged_model_uri` **and `logged_model_id`** (the MLflow 3 `LoggedModel` id — metrics attach to a *(model, dataset)* pair via `log_metric(..., model_id=..., dataset=...)`, and `ModelVersion.model_id` does **not** auto-populate in OSS MLflow, so this id must be persisted deliberately or the registry cannot reach the model it points at), and `tuning_summary` (trial counts, selected vs. raw-best trial number/score, 1-SE standard error and band floor — the diagnostics behind the `selection_rule` pick).
- **Persist the evidence, not just the conclusion.** Any module whose output rests on a computed array must **log that array**, not only the summary or the chart derived from it. Re-derivation is only sound while the dataset is static and the folds are seeded; under retraining it silently reconstructs *different* numbers than the ones that cycle's decisions rested on, and nothing flags it. Concretely:
  - `calibrate.py` selects the calibration method, reports BSS/ECE, and validates `t*` from the dev-OOF probability vector — so it logs **`dev_oof_predictions.parquet`** alongside `calibration_summary.json`. Downstream (the drift reference's score baseline, the dev-OOF veto surface, the calibration screen) then reads the exact numbers the decision was made on.
  - `error_analysis.py` renders SHAP charts — so it logs **`shap_values.parquet`**, not only the figures. A rendered plot answers the question you thought to ask; the values answer the one you did not.
- **Evaluation (Phase 7 `evaluate.py`) gets its own `evaluation` run, artifacts foldered, metrics namespaced `test_*`.**
  - **Its own run — a sibling of `model_comparison` / `tuning_study`**, following the step-per-run pattern. Not appended to the `dev` version's run: that run already holds Phase 5's pipeline + manifest and Phase 6's calibrated model + calibration summary, and Phase 10 needs each cycle's evaluation runs to be comparable peers in the UI.
  - **Linkage is native — this project runs MLflow 3.16.** A logged model is a first-class `LoggedModel` with its own `model_id`, and **metrics attach to a (model, dataset) pair**: `mlflow.log_metric(..., model_id=..., dataset=...)`. Log every evaluation metric with both. The metrics then belong to the *model*, not to whichever run computed them — so a separate evaluation run stays fully attributable. **Do not hand-roll this with tags.** Consequence: Phase 5/6 must record `logged_model_id` (from `log_model`'s returned `ModelInfo`) in `training_manifest.json`, or Phase 7 has nothing to log against.
  - **The CV-vs-test collision is structural, and the dataset dimension is what resolves it.** Phase 5's `pr_auc` (dev, cross-validated) and Phase 7's `pr_auc` (sealed test) are different quantities that must never be conflated. Keyed by dataset, they are distinct rows. Keep a `test_` prefix as well — not for correctness now, but because metric keys surface in search/exports where the dataset column is not shown.
  - **The four gate criteria are also set as model-version tags** (`test_pr_auc`, `test_recall`, `test_brier`, `test_calibration_slope`), by `register.py`, on **every** version it processes — promoted or rejected, not only the ones that end up serving. `LoggedModel` metrics answer *"what did this model score?"*; the **registry** is where a rollback is chosen, under pressure, by someone scanning a version list — and this is exactly where those numbers must be legible without opening a run, including for a rejected candidate a reviewer is trying to understand.
    **Shipped in Phase 10a-ii, ahead of `training_cycle.py` (Phase 10b) actually calling either gate module:** on a routine retrain cycle, these four tags alone are not sufficient — `pipelines/performance_check.py::run_performance_check`'s `decide_promotion` call gates on the **reserve comparison cohort**, a different evaluation surface than the sealed-test values these tags carry, so the tags are diagnostic-only there (still comparable across every cycle, still worth keeping) rather than the numbers that actually decided anything. Two more tags close that gap, both written by `register.py`'s `_tag_gate_source`: `gate_source` (`"evaluate"` / `"performance_check"` / `"v1_cold_start"` — which module's run produced the binding decision, derived from `mlflow.get_run(eval_run_id).info.run_name` plus `promotion_decision.json`'s own `regime`) and `gate_pr_auc_delta` (the actual admitting criterion on a `performance_check`-gated cycle, populated only then). See `PROJECT_PLAN.md`'s Phase 10a-ii `register.py` walkthrough for the full reasoning.
  - Artifacts sit at the run's root (`metrics.json`, `economics.json`, `promotion_decision.json`, the prediction parquets), with sub-paths only where they separate different *kinds* of output — `figures/`, `slices/`. Do not prefix them `evaluation/`: the run already is the evaluation. Sliced/fairness detail is an **artifact**, not hundreds of metric keys — except `test_equal_opportunity_diff` and `test_demographic_parity_diff`, which gate §0's V2 and should be plottable across cycles.
  - **Business metrics are metrics — but they are not model properties, and the cost inputs must be logged alongside them or they are uninterpretable.** Expected value, campaign cost, retained revenue, contacted count, and break-even retention rate are logged as MLflow metrics per scenario (plus the `treat-all` / `treat-none` baselines), because Phase 10 needs them plottable across cycles. **But `test_ev_base` moves when the model changes *or* when `configs/costs.yaml` changes, and in the UI those causes are indistinguishable.** So log the cost inputs as **run params** and set a **`costs_config_hash` tag**: same hash ⇒ the model changed; different hash ⇒ the assumptions did. The supporting arrays (EV-vs-K curve, sensitivity sweeps, break-even grid) go to `economics.json`, not metric keys. **EV is never a model-version tag** — those carry exactly the four gate criteria, and that set is legible precisely because it is exactly the criteria; §0 makes EV a diagnostic, so tagging it onto the version invites a rollback decision on a number no gate ever admitted.
- **`drift_reference.json` — written once, at champion promotion (Phase 7 `register.py`).** The baseline every Phase 10/13 drift check measures against: per-feature reference distributions, the reference prediction-score distribution, and the reference churn prevalence. Two rules, both mandatory:
  - **MUST be logged as an MLflow artifact on the promoted run, and MUST be read back by resolving the `champion` alias.** Never `reports/drift_reference.json` as the source of truth — a copy may be mirrored there for human inspection, but no code may *read* it. The reference travels with the model version or the system lies: an emergency rollback re-points `champion` at version N−1, and a fixed-path reference does not roll back with it, so every subsequent drift check compares live traffic to the *previous* champion's score distribution and reports drift that is really the model swap you just performed. The prediction-score half of the reference is genuinely model-specific (v3 and v4 score customers differently); the feature half is closer to a data property and would survive the mismatch — it is the score half that produces the phantom alerts. `register.py` writes it via `mlflow.log_artifact` onto the promoted run; `pipelines/drift_check.py` fetches it from the `champion`-aliased run. **A refactor that reads the reference from a fixed path is a correctness regression, not a simplification** — same footing as `evaluate.py`'s resolve-by-`run_id` rule.
  - **The score baseline MUST be built from out-of-sample probabilities** (dev-OOF ∪ sealed-test — all 7,043 rows, each scored by a model that never trained on it), *never* from the champion scoring its own training data. In-sample scores are systematically sharper, and baselining on them produces a permanent phantom PSI signal against honest production scores that no amount of investigation will resolve. Feature distributions have no such problem and come from the champion's actual training data.
- **`model_card.json` — written once, at champion promotion (Phase 7 `register.py`), not at Phase 6 challenger registration.** Stakeholder-facing narrative: intended use, known limitations, performance summary **vs. the decision-relevant baselines**, fixed-recall profile, fairness/robustness flags. **Those baselines are `treat-none` / `treat-all` and the `DummyClassifier` prevalence floor — never LogReg.** LogReg was a candidate in Phase 5's *family comparison*, not a rival to the champion; a stakeholder needs to know what the model buys over doing nothing and over the naive policy, not which algorithms lost. Nor should it be re-scored on the sealed test set to fill this line: the family decision rests on 100 paired CV folds, and a single 1,409-row holdout would yield a *noisier* Δ that reads as *more* authoritative for being a "test-set number" — a straight downgrade. The family comparison belongs in `ANALYSIS.md` §4 and `training_manifest.json`'s paired-Δ, which already carry it. It is not populated when `register.py` mints the challenger — at that point the model is calibrated but un-thresholded and untested on the sealed set, so a "known limitations" section would still be a disclaimer about an unfinished product. No hyperparameters, hashes, or raw statistical detail either way — that lives in `training_manifest.json`. **Assembled from artifacts, never hand-transcribed:** performance and the fixed-recall profile come from `metrics.json` (resolved via the model version's `eval_run_id` tag, tagged by `register.py`); the fairness/robustness flags and known limitations come from `error_analysis.json`, computed by **`models/error_analysis.py`**, not the notebook — it is a pipeline artifact, and Phase 10's automated retrain has no human to run Jupyter — and resolved via `error_analysis_run_id`, tagged onto the model version by `register.py` (from `reports/error_analysis_receipt.json` on its first pass for this version, from the tag itself thereafter). `register.py` **aborts if it cannot resolve an `error_analysis_run_id` for the version, or if that run has no `error_analysis.json`** — a fairness section retyped from a rendered notebook cell is exactly the section that gets quoted back at you, and it must be reproducible from the artifact that produced it. `business_case.expected_impact.capacity_budget_check` is read the same way, off `economics.json` on the same `eval_run_id` (no new resolution — `register.py` already loads this artifact for `ev_by_k_logged`), and is `None` rather than aborting when the eval run predates it or otherwise has no `economics.json`, since a capacity/budget breach is a diagnostic (§0: EV and its supporting economics never gate) and unlike the fairness/limitations fields above has no promotion decision riding on it.
